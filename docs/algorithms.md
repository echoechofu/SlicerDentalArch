# Algorithm usage and measurement protocol

[中文说明](algorithms.zh-CN.md) · [Project overview](../README.md) · [Editor guide](editor.md)

## 1. Accepted input and scope

The current implementation accepts a complete upper arch with 14 separately
connected crown components: central incisor, lateral incisor, canine, two
premolars and two molars on each side. Extra components such as a base may remain
in the STL and are excluded through the reviewed tooth map.

This is **not tooth segmentation from a fused scan**. Component discovery joins
triangles across shared manifold edges; the input must already have the required
independent crown surfaces. Every selected crown must be a closed, consistently
outward oriented manifold with no degenerate triangles. The loader does not
repair, rescale, fill holes, or infer a missing tooth.

Only binary STL with the exact declared triangle-record length is accepted.
Vertex matching is exact, without a welding tolerance. Exporting, reordering
triangles, repairing or modifying the STL changes its source hash and can change
component IDs: inspect and review the new file again.

The frame, tooth identity and anatomical interpretation require review. This
release does not support partial arches, missing teeth, third molars, lower
arches, or automatic mapping to a clinical tooth-numbering system.

## 2. Inspect and review

Use Slicer's Python runtime for all algorithm commands. The examples below are
PowerShell commands run from the repository root; substitute your own paths.

```powershell
& "C:\path\to\Slicer\bin\PythonSlicer.exe" algorithms/inspect_stl.py --input model.stl --output-dir work/inspect
```

The inspection stage writes:

| File | Purpose |
| --- | --- |
| `components.json`, `components.csv` | Component IDs, bounds and mesh checks |
| `inspection_top.png`, `inspection_bottom.png` | Overview in the proposed frame, labelling the 32 largest components |
| `config.template.json` | Source-bound configuration with unassigned groups and false review flags |

Copy the template into a private configuration file. Check the mesh in 3D as well
as the overview images. The PCA orientation is only a proposal: axis ordering and
signs must be anatomically reviewed before a top-surface detector is meaningful.

The aligned coordinates are:

```text
q = (native_coordinate - alignment.center) @ alignment.axes_columns
native_coordinate = q @ alignment.axes_columns.T + alignment.center
```

The three columns define the transverse, anterior and occlusal directions.
Review that positive qY points anteriorly and positive qZ points toward the
occlusal/incisal surfaces. In the occlusal preview with qY pointing up, VL occupies
the negative qX side and VR the positive qX side. The matrix must be orthonormal and right-handed; it
cannot contain scaling or shear. Rotation changes the analysis frame, not the
stored native coordinates.

### Configuration contract

Edit the generated template rather than constructing a configuration from an
unrelated case.

| Key | Required value |
| --- | --- |
| `schema_version` | `1` |
| `sha256` | Digest of the exact reviewed STL, generated by inspection |
| `alignment.center` | Three finite native coordinates |
| `alignment.axes_columns` | A finite 3 × 3 orthonormal, right-handed matrix |
| `orientation_reviewed` | `true` after visual frame review |
| `tooth_mapping_reviewed` | `true` after component-to-tooth review |
| `regions` | All 14 entries, each with its expected `id`, `kind` and distinct nonnegative integer `group` |
| `groove_anchors` | Optional premolar ID → two distinct aligned XY cusp anchors |

There are seven labels for each of `VL` and `VR`:

| Suffix | Kind |
| --- | --- |
| `I1` | `central_incisor` |
| `I2` | `lateral_incisor` |
| `C` | `canine` |
| `P1`, `P2` | `premolar` |
| `M1`, `M2` | `molar` |

These side labels belong to the input coordinate convention, not an inferred
patient left/right or FDI numbering. Confirm identity from the original model.
Do not merely change both review flags to bypass missing review.

Optional premolar `groove_anchors` are pairs of buccal/lingual cusp positions
expressed as `[[qX, qY], [qX, qY]]`. They establish a corridor for searching the
central groove; they are not the final M/D points. Without supplied anchors, the
pipeline provisionally uses two detected cusp candidates and stops if a premolar
does not provide both candidates. Both cases still need
anatomical review of the resulting groove direction and width points.

### Coordinate scale

Output lengths remain in native coordinate units. No physical unit is inferred.
The detector uses fixed native-unit search distances, for example height-map
sampling, smoothing and candidate separation. Its defaults were developed on
dental-sized, millimetre-like coordinates. Check component bounds and the
parameters in the algorithm source before using another scale. The reference
fit normalizes its optimization coordinates, but that does not make the upstream
landmark and width algorithms scale-independent.

## 3. Run the pipeline

Create both algorithm results and an initialized Slicer scene:

```powershell
& "C:\path\to\Slicer\Slicer.exe" --ignore-slicerrc --disable-settings --no-main-window --no-splash --python-script algorithms/run_in_slicer.py -- --input model.stl --config reviewed.json --output-dir output/session
```

Use a new or empty output directory. The entry point refuses to overwrite an
existing result. This command launches a fresh batch Slicer process; save work in
any other Slicer session independently.

To run the numerical stages only:

```powershell
& "C:\path\to\Slicer\bin\PythonSlicer.exe" algorithms/run_all.py --input model.stl --config reviewed.json --output-dir output/session
```

Add `--skip-sensitivity` to either command to omit additional incisal, width and
reference-arch sensitivity runs. These assess parameter sensitivity, not clinical uncertainty.

| Output | Contents |
| --- | --- |
| `landmarks/landmark_candidates.json` | Cusp and fossa candidates in native/aligned coordinates |
| `incisal/incisal_results.json` | Four incisal curves and midpoint results |
| `mesiodistal/mesiodistal_results.json` | Per-tooth M/D points, axes, widths and review information |
| `arch/reference_arch_results.json` | Analytic curve definition, plane, endpoint and fit metadata |
| `crowding_results.json` | Required/available lengths and their signed difference |
| `resolved_config.json` | Configuration used for this run |
| `pipeline_manifest.json` | Stage and source provenance |
| `DentalArchScene.mrb` | Self-contained scene with initialized baseline and working editor state |
| `scene_validation.json`, `pipeline_status.json` | Scene creation checks and batch completion state |

Stages also write supporting CSV results. Scene-related outputs require
`run_in_slicer.py`. Treat all outputs, including configuration files, source
hashes, reports, screenshots and coordinates, as part of the private case data.

## 4. What the algorithms do

### Cusps and central fossae

Each crown is represented as an occlusal height map. Detrending, smoothing at
multiple scales and convexity/local-height criteria produce cusp candidates.
The candidate caps are one per canine, two per premolar and four per molar:
at most 26 cusps for this 14-tooth setup, not a guaranteed count. An interior
concavity search proposes central fossae for the four molars when supported by
the surface. Confidence and geometry checks are heuristics, not probabilities
of anatomical correctness.

### Four incisal edges

Only the four incisors receive incisal-edge curves. A high occlusal ridge band
and a smoothness-constrained path search propose a curve, which is projected back
onto the tooth surface. The curve and its midpoint are exported. Endpoint choice
is heuristic. Canines use cusp points; canine ridges are outside this scope.

### Mesiodistal points, version 2

For premolars, a central-groove search uses the corridor between opposing cusp
anchors, concavity/slope evidence and a smooth path. Its fitted direction guides
the M/D chord. Molars use the crown outline to estimate the direction. Candidate
posterior endpoints are restricted to the **upper third of the separated crown's
geometric height**, normalized along reviewed qZ, and a surface chord search uses
opposing proximal normals while rejecting intervening surface crossings.

This height is not a clinically identified cemento-enamel junction or a fitted
individual tooth axis. A wrong separation boundary or global orientation changes
its meaning. Incisors retain the anterior width method.

The output is an intrinsic M/D **width-point pair** on each crown. It need not
coincide with physical contact between neighbouring teeth, particularly where
teeth are rotated or spaced. Review the premolar groove direction, endpoint
height and tooth association in the scene.

### Reference arch

The default reference is a planar cubic B-spline with seven controls. It follows
the current overall arch form while smoothing local displacement, without
imposing bilateral symmetry. The 20 M/D points from P2 to contralateral P2 provide
the fit data. The projected first-molar mesial points are fixed endpoints.

The fit gives equal total weight to each tooth, uses a Huber residual with a
second-derivative smoothness penalty, and solves in normalized coordinates.
The defaults use a penalty weight of `1e-4` and a Huber transition of 1.5% of the
endpoint distance. See the source for the exact solver and optional sensitivity
variants. The curve's controls, knot vector and degree are authoritative; its
501-point sample is for display.

The reference plane is parallel to reviewed qXY at the mean qZ of the two
first-molar mesial endpoints. Source-point height variation does not inflate
available length.

## 5. Space analysis as a mathematical problem

Let `M_i` and `D_i` be native 3D width points for the ten teeth from P2 to P2.
Let `B(t)` be the planar analytic reference curve between projected M1 mesial
endpoints.

```text
w_i = ||M_i - D_i||₂
R   = Σ w_i
A   = ∫₀¹ ||B′(t)||₂ dt
C   = R - A
D   = A - R
```

Positive `C` denotes a net shortage and negative `C` a net surplus in the native
coordinate units. First-molar widths are excluded; second molars are outside the
measurement span. This is one explicit reference-curve protocol, not every
clinical space-analysis convention. It does not assign severity or prescribe an
arch expansion. A net surplus may coexist with local crowding or rotations.

## 6. Review and revise in Slicer

Install and open DentalArchEditor, then open the generated MRB. Algorithm results
are preserved as the baseline and a separate state is available for editing.

Internal width-point edits change required length without silently refitting
the interior arch. The two first-molar mesial endpoints remain linked to the
arch boundaries. Five interior curve controls are free; the two end controls
are bound. Use explicit **Refit** when a new fit is desired.

Manual edits can depart from algorithm proposals. The editor reports review
warnings for direction/height deviations; it does not silently move the point
back to an algorithm result. Refer to the [editor guide](editor.md) for
surface snapping, curve validity, transform restrictions, undo and revision
saving. An MRB stores data, not Python callbacks: the installed module must be
opened to resume live calculation after loading.

## Troubleshooting

| Symptom | Action |
| --- | --- |
| Only one fused arch component | Segment and prepare separate crowns before using this pipeline |
| Open/nonmanifold/inward crown rejected | Correct the mesh in an appropriate preparation tool, then inspect and review the new STL |
| Hash mismatch | Reinspect the exact file; do not reuse a map from a changed export |
| Review flags false or missing groups | Complete the frame and 14-tooth mapping review |
| Points appear on the underside | Recheck occlusal qZ direction and crown boundaries |
| Unexpected candidate counts or poor premolar direction | Check scale, topography, crown mapping and cusp/groove anchors; review manually |
| Result directory already exists | Choose a fresh output directory |
| MRB opens but values do not update | Install/open DentalArchEditor and use the saved initialized scene |
